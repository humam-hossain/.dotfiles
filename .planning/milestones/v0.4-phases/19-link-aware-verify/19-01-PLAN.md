The D-26 guard, as a FUNCTION and not as inline code at the call site: `guard_scratch_target()`, taking the path about to be destroyed as `$1` and reading `$T_REAL` from the enclosing scope. It resolves its argument at call time with `realpath` and fails closed — an unresolvable or empty result, or an empty `$T_REAL`, is a refusal, never a pass. On the resolved value it takes a `case` that returns 0 only on a strict prefix match under `$T_REAL/`, and otherwise writes on fd 2 exactly one `[FAIL]` line naming BOTH resolved values, the resolved target and the resolved scratch root, then returns non-zero. It must `return`, never `exit`, so its refusal can be captured and asserted. Write that line as a bare `echo … >&2` and do NOT route it through the script's `fail()` emitter: `fail()` increments the FAIL counter, and the probe below expects two refusals, so routing them through it would end an entirely correct run at `FAIL=2` and exit 1. A refusal the harness asked for is not a harness failure. It reads nothing the code under test produces and calls nothing the code under test defines. It performs no destruction of any kind: `rsync` appears only at its call site and never inside it, which is precisely what makes it safe to point at real paths in the probe below.

The single `rsync -a --delete` call site is gated on that same function — set `victim` to the fixture's live package directory and write `guard_scratch_target "$victim" || exit 1` immediately above the destructive command. One definition, one gate: a guard proven in one place and re-typed at the call site is not proven at all.
