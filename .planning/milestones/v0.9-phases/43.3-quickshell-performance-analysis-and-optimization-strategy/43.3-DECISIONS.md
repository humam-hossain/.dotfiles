# Phase 43.3: Quickshell Architectural Optimization Decision Matrix

**Date:** 2026-09-27  
**Status:** Formalized & Locked  
**Phase:** 43.3 (Quickshell Benchmark Bottleneck Analysis & Optimization Strategy)  
**Empirical Baseline Reference:** Phase 43.2 (`BENCHMARK.md`)  
**Target Environment:** pera-desktop (Intel Core i7-12700K, Intel UHD Graphics 770, DP-1 3440x1440@60Hz)

---

## 1. Overview & Decision Framework

This document formalizes all 12 architectural optimization decisions (D-01 through D-12) established during Phase 43.3. These decisions directly resolve the empirical bottlenecks identified during Phase 43.2 baseline benchmarking:
1. **Idle Syscall Churn:** ~3,120.9 read syscalls/s and 476.1 voluntary context switches/s (132x pure upstream baseline).
2. **Active Inspector Overhead:** +8.14% CPU, +648.8 context switches/s, and +14.41% Intel UHD 770 iGPU load (pushing iGPU load to 26.41%).
3. **Scenegraph & Animation Footprint:** Unthrottled animations and dynamic property bindings firing during normal operating conditions.

Every decision below is documented with its technical context, evaluated alternatives, pros/cons, and reversibility rating.

## 2. Formal Architectural Decisions (D-01 to D-12)

### D-01: Rollout Timing & Empirical Verification (Phase 43.4 Insertion)
- **Context:** Optimization changes directly touch core status bar telemetry and rendering loops. Implementing and verifying them in one monolithic step risks conflating causes if regressions occur. Furthermore, the operator requested a complete benchmark re-run capturing both the clean upstream baseline and custom shell side-by-side in `BENCHMARK.md`.
- **Alternatives Evaluated:**
  - *Option A:* Bundle optimizations into Phase 44 (*Memory & Storage Telemetry*).
  - *Option B (Selected):* Insert dedicated Phase 43.4 (*Quickshell Targeted Optimization & Empirical Verification*) immediately preceding Phase 44.
- **Pros:** Isolates performance improvements; provides side-by-side empirical validation (`BENCHMARK.md`) before expanding shell scope.
- **Cons:** Adds an inserted phase to Milestone v0.9 roadmap.
- **Reversibility:** Reversible (roadmap adjustment).
- **Execution Target:** Phase 43.4.

---

### D-02: Demand-Gated Adaptive Polling (`ResourceUsage.qml`)
- **Context:** `ResourceUsage.qml` initializes `Timer` with `interval: 1` and attempts imperative assignment `interval = 3000` inside `onTriggered`. In QtQuick, this causes the timer to fire at 60–100Hz continuously, generating ~3,100 read syscalls/s against `/proc/meminfo` and `/proc/stat`.
- **Alternatives Evaluated:**
  - *Option A:* Fix the imperative timer by stopping, setting interval, and restarting.
  - *Option B (Selected):* Configure declarative timer initialized with `interval: isInspectorActive ? 1000 : (Config?.options?.resources?.updateInterval ?? 3000)` and trigger immediate startup acquisition via `Component.onCompleted`.
- **Pros:** Completely eliminates the `interval: 1` scheduler recursion; ensures declarative reactivity; drops idle read syscalls by ~3,000/s.
- **Cons:** Requires adding `isInspectorActive` property or binding.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-03: History Array GC Optimization (`ResourceUsage.qml`)
- **Context:** Every tick of `ResourceUsage.qml` spreads arrays into new instances (`cpuUsageHistory = [...cpuUsageHistory, newPoint]`), triggering constant V8/QJSEngine garbage collection churn even when no chart or popup is open.
- **Alternatives Evaluated:**
  - *Option A:* Maintain ring buffers with in-place index manipulation.
  - *Option B (Selected):* Gate history array updates (`cpuUsageHistory`, `memoryUsageHistory`, `swapUsageHistory`) on inspector active state (`isInspectorActive`), skipping history accumulation while uninspected.
- **Pros:** Eliminates continuous heap array allocations and garbage collection cycles during idle.
- **Cons:** History graph starts populating from the moment inspector opens rather than maintaining 60s background history.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-04: Retire Legacy Resources Pill Ahead of Phase 44 (`BarContent.qml`)
- **Context:** The status bar currently hosts both `Resources.qml` (consuming `ResourceUsage.qml`) and `CpuGpuPill.qml` (consuming `HardwareTelemetry.qml`). Phase 44 introduces `MemoryStoragePill.qml`, which supersedes `Resources.qml`.
- **Alternatives Evaluated:**
  - *Option A:* Keep `Resources.qml` active until Phase 44 is fully implemented and verified.
  - *Option B (Selected):* Retire `Resources` pill from `BarContent.qml` and `VerticalBarContent.qml` in Phase 43.4, leaving `ResourceUsage.qml` dormant/lightweight and cleanly preparing the Left Zone for Phase 44.
- **Pros:** Eliminates redundant status bar UI immediately; frees status bar real estate; reduces idle telemetry consumers.
- **Cons:** Status bar temporarily lacks a dedicated RAM percentage pill until Phase 44 mounts `MemoryStoragePill.qml`.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-05: Two-Tier Demand-Gated Sweeping (`HardwareTelemetry.qml`)
- **Context:** `HardwareTelemetry.qml` defines 31 active `FileView`s (hwmon temps, nvme, mobo, cpufreq, drm). The status bar pill only displays `overallCpuLoad`, `packageTemp`, and `gpuLoad`, yet all 31 files are swept every 3s in idle.
- **Alternatives Evaluated:**
  - *Option A:* Continue sweeping all 31 files but stagger reads across multiple timer ticks.
  - *Option B (Selected):* Split polling into two tiers:
    - *Tier 1 (Idle 3000ms):* Sweep strictly 3 files (`/proc/stat`, package temp, iGPU RC6).
    - *Tier 2 (Active 1000ms):* Sweep remaining 28 sensors strictly when `fastPollingRequests > 0`.
- **Pros:** Eliminates 28 sysfs/procfs reads per cycle during idle; drops context switches by ~150/s.
- **Cons:** Requires segregating FileView reload logic into tier-specific functions.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-06: Zero-Latency First Frame on Popup Open (`HardwareTelemetry.qml`)
- **Context:** When transitioning from Tier 1 (3 files) to Tier 2 (all 31 files), waiting for the next 1000ms timer tick would leave core meters blank or displaying stale data for up to 1 second upon opening the popup.
- **Alternatives Evaluated:**
  - *Option A:* Accept a 1-tick warmup delay.
  - *Option B (Selected):* On `fastPollingRequests` incrementing from 0 to 1, trigger an immediate synchronous sweep of Tier 2 sensors.
- **Pros:** Zero-latency UI response; all 20 thread meters populate on frame 0 with zero visual stutter.
- **Cons:** Slight CPU cost at the exact moment of popup click (acceptable interaction trade-off).
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-07: Timer Cadence Specification (`HardwareTelemetry.qml`)
- **Context:** Telemetry cadence must balance responsiveness against background wakeups and context switches.
- **Alternatives Evaluated:**
  - *Option A:* 2000ms idle / 500ms active.
  - *Option B (Selected):* Maintain 3000ms idle interval (minimal background wakeups, ~1 read/s) accelerating to 1000ms active interval when inspecting.
- **Pros:** Consistent with human perceptual requirements for system monitoring while keeping idle thread wakeups negligible.
- **Cons:** None.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-08: Unified Telemetry Consolidation (`HardwareTelemetry.qml` & `ResourceUsage.qml`)
- **Context:** Both `ResourceUsage.qml` and `HardwareTelemetry.qml` independently open and parse `/proc/stat` to calculate CPU load, resulting in duplicate procfs parsing.
- **Alternatives Evaluated:**
  - *Option A:* Keep independent procfs reads in each service.
  - *Option B (Selected):* Consolidate CPU procfs telemetry into `HardwareTelemetry.qml`, deprecating duplicate reads in `ResourceUsage.qml`.
- **Pros:** Single source of truth for CPU utilization; saves duplicate kernel parsing and string allocations.
- **Cons:** Requires consumer components to source CPU metrics from `HardwareTelemetry`.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4 / Phase 44.

---

### D-09: Full 20-Thread Meter Layout Retained (`CpuGpuPopup.qml`)
- **Context:** Opening `CpuGpuPopup.qml` instantiates 20 `ThreadMeter` items, driving iGPU load to 26.41%. Condensing the UI was considered.
- **Alternatives Evaluated:**
  - *Option A:* Condense 20 thread meters into 2 cluster summary bars (P-cluster and E-cluster).
  - *Option B (Selected):* Preserve the full 20-thread layout (12 P-threads, 8 E-threads) while eliminating rendering overhead via binding guards and animation throttling.
- **Pros:** Preserves the rich, detailed inspector UX desired by the operator.
- **Cons:** Requires strict scenegraph optimization to keep rendering lightweight.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-10: Strict Critical Pulse Gating (`CpuGpuPill.qml` & `CpuGpuPopup.qml`)
- **Context:** The critical alert breathing animation (`SequentialAnimation` pulsing opacity between 0.4 and 1.0) must not run when metrics are within normal ranges.
- **Alternatives Evaluated:**
  - *Option A:* Leave animation running with opacity range 1.0 -> 1.0 when not critical.
  - *Option B (Selected):* Enforce strict condition gating (`running: root.active && root.isCritical`) so the animation is completely stopped and detached from the QtQuick scenegraph frame clock during normal operation.
- **Pros:** Eliminates 60fps frame ticker wakeups when system metrics are normal.
- **Cons:** None.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-11: 1% Integer Deadband Quantization (`CpuGpuPopup.qml` & `CpuGpuPill.qml`)
- **Context:** Continuous micro-fractional floating-point fluctuations (e.g. 14.234% -> 14.281%) cause constant QML property re-evaluations, layout recalculations, and repaint passes.
- **Alternatives Evaluated:**
  - *Option A:* Pass raw unquantized floats directly to UI bindings.
  - *Option B (Selected):* Apply 1% integer deadband quantization (`Math.round(val * 100) / 100`) on progress meters and gauges.
- **Pros:** Prevents sub-pixel rendering churn and unnecessary scenegraph dirty flags.
- **Cons:** Micro-fluctuations below 1% are not visually reflected (imperceptible to human eye).
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.

---

### D-12: Popup Inactivity Binding Guards (`CpuGpuPopup.qml`)
- **Context:** When the popup is hidden/closed, any property updates from `HardwareTelemetry` that are bound to popup elements can cause background layout passes and expression evaluations.
- **Alternatives Evaluated:**
  - *Option A:* Rely solely on window visibility flags.
  - *Option B (Selected):* Guard all inner item bindings, layout passes, and NumberAnimations in `CpuGpuPopup.qml` on `root.active`.
- **Pros:** Zero UI evaluation or scenegraph overhead while popup is closed; complete CPU/GPU decoupling during idle.
- **Cons:** Requires `active` guards on binding expressions.
- **Reversibility:** Reversible.
- **Execution Target:** Phase 43.4.
