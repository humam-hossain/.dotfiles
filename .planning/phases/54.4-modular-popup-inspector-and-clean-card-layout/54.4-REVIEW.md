# Phase 54.4: Code Review Report

**Reviewed:** 2026-10-17

## Summary

The diff splits the weather graph into a pure JS module (`WeatherGraphMath.js`) and one `WeatherGraph.qml` card used three times. It also replaces the fixed 880px scrolling popup with a non-scrolling popup sized as a percent of the screen, adds a shared hover slot with a popup-level tooltip overlay, and updates four assert harnesses.

Structural QML checks pass:
- `WeatherPopup.qml` has one top-level `Item`. The `Connections` sits inside `contentRoot`.
- `WeatherGraph.qml`'s top-level `Connections` lands in `WeatherBaseCard`'s `default property alias content: cardContent.data`, which is a `list<QtObject>`, so it loads.
- Every id resolves (`graphArea.parent.parent` is `layout`, so `plotOriginX/Y` add up to the right offsets).
- Every delegate uses `required property`.
- No synchronous binding loop was found.

In the JS math, all divisions are guarded: `valueToY` handles a flat scale, `_barRects` requires `max > 0`, the wind and UV scales are floored at 1, and the temperature scale is never flat. Hover index, scrub line, markers, ticks and canvas columns all use the same `plotLeft + (i + 0.5) * slotW` slot model, with no off-by-one.

Main concerns:
1. **Popup placement.** The popup is now sized from the real screen, but `StyledPopup` still clamps its position against a hard-coded 1920px. `QsWindowAttached` has no `screen` property, so the fallback always applies. On this host's 3440px-wide DP-1 the popup is pinned to the far left. The new re-clamp `Connections` cannot fix this.
2. **Tooltips.** All three tooltips show at once and can overlap when they are wider than their card.
3. **Regression harness.** `phase54-weather-assert.sh` exits 1 after this phase (3 S3 FAILs from the code move).
4. **Fixed palette.** The colours are only contrast-checked against dark surfaces; the wind series is pure white.

## Critical Issues

### CR-01: Popup position is clamped against a hard-coded 1920px screen; the new re-clamp hook cannot work

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/StyledPopup.qml:89`, `:100`, `:124-129` (with `WeatherPopup.qml:51-62`)

**Issue:** `updateLockedMargins()` reads `root.QsWindow?.screen?.width ?? 1920`. `QsWindowAttached` only exposes `window`, `contentItem`, `itemPosition`, `itemRect` and `mapFromItem`; it has no `screen` (see `/usr/lib/qt6/qml/Quickshell/_Window/quickshell-window.qmltypes:520-560`). So `screenWidth` is always 1920 and `screenHeight` is always 1080.

Before this phase the popup was a fixed 880px, so the error was small. Now `WeatherPopup` sizes itself from the real screen (`contentRoot.QsWindow?.window?.screen`) at 50% width with a 900px minimum:
- **DP-1 (3440x1440, scale 1):** the content is 1680px and `popupBackground.implicitWidth` is 1700. That gives `maxX = 1920 - 1700 - 5 = 215`. Wherever the weather pill sits, the popup's left margin is clamped to 215px or less. A pill at x≈2400 gets its popup about 1300px to its left.
- **HDMI-A-2 (portrait at 1.5x, about 720px logical width):** `maxX` is computed against 1920, so the popup can run past the right edge of the output.

The new `Connections { target: popupBackground; onImplicitWidthChanged ... }` is commented "Re-clamp ... after the screen becomes known". It cannot do that, because the clamp never reads the real screen.

**Fix:** Resolve the screen through the attached window, the same way `WeatherPopup` and `BarContent` do:
```qml
function updateLockedMargins() {
    const scr = root.hoverTarget?.QsWindow?.window?.screen ?? popupWindow.screen;
    if (!Config.options.bar.vertical) {
        const screenWidth = scr?.width ?? 1920;
        ...
    } else {
        const screenHeight = scr?.height ?? 1080;
        ...
    }
}
```
Also set `screen: root.hoverTarget?.QsWindow?.window?.screen ?? null` on the `PanelWindow`. Then the popup opens on the bar's output, and `WeatherPopup`'s size and `StyledPopup`'s clamp use the same screen.

## Warnings

### WR-01: Three simultaneous tooltips overlap each other when one is wider than its card

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherPopup.qml:184-216`

**Issue:** `tooltipLayer` shows one tooltip per graph whenever `hoverSlot >= 0`, so three tooltips appear at once. When `tip.width > tip.modelData.width`, `x` is only clamped to the whole layer (`Math.max(0, Math.min(tooltipLayer.width - tip.width, want))`). It can then float over a neighbouring card, where that card's own tooltip is already drawn.

At the 900px minimum outer width each card is about 298px wide. Realistic airuv line 3 (`"AQI Unhealthy for Sensitive · PM2.5 35 · PM10 50"`) or a long `desc` header at 12px exceeds that. For late slots the airuv tooltip is clamped to the layer's right edge and its left edge overlaps the rain card's tooltip, so the text is drawn on top of other text. No check prevents this.

**Fix:** Either show the tooltip only for the card under the cursor (record the source graph id with `hoverRequested`), or bound each tooltip to its own card and wrap its text:
```qml
// in tipBody / text rows
Layout.maximumWidth: tip.modelData.width - 20
wrapMode: Text.WordWrap
```
and drop the "float over neighbours" branch.

### WR-02: `phase54-weather-assert.sh` now exits non-zero: three S3 asserts fail after code moved to WeatherGraphMath.js

**File:** `scripts/phase54-weather-assert.sh:390-421`

**Issue:** This phase edited the harness (commit 27f252a6) but left section 3 grepping `WeatherGraph.qml` for code that has moved to `WeatherGraphMath.js`:
- `bezierCurveTo` and `computeMonotoneSplineControlPoints`
- `time.*!==.*"24"`, which is now `String(raw.time) === "24"` in GM
- `tooltipPill` and `snapDot`, which are now the popup tooltip overlay

A run during review gives `FAIL=4` and exit 1. Three of the four FAILs come from this phase. `phase54.3-weather-assert.sh` was updated to turn the same moved contracts into INFO lines, but phase 54 was not. The phase 54 regression gate is red.

**Fix:** In S3, point the moved checks at `$WEATHER_MOD_SRC/WeatherGraphMath.js`, matching `String\(raw\.time\) === "24"`. Turn `tooltipPill`/`snapDot` into `info "S3: superseded by D-54.4-08 ..."`, the same pattern used in `phase54.3-weather-assert.sh`.

### WR-03: The fixed palette ignores the light theme; wind and gust are pure white

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:42`, `:1111-1112`, `:67`; `WeatherGraph.qml:222`

**Issue:** `WIND_COLOR = "#ffffff"` (alpha 0.9) is used for:
- the wind and gust lines
- their markers
- their peak labels
- the legend dot and the legend label text (`color: entry.modelData.color`)

In a light Material scheme, `colLayer2` is near white, so these elements disappear. `PRESSURE_COLOR "#b0bec5"` and the yellow tiers (`#ffee58`) are also near-invisible on light surfaces. The PA-3 contrast checks in `phase54.4-weather-assert.sh` only test against the dark surfaces `#1f2020` and `#292a2a`.

**Fix:** Pass the on-surface colour through `theme()`, for example `theme().text`, and use it for wind and gust instead of `WIND_COLOR`. Draw legend labels with `Appearance.colors.colOnSurfaceVariant` and keep the palette colour only for the swatch. Alternatively, keep separate light and dark palettes selected by `Appearance.m3colors.darkmode`, and add light-surface rows to the contrast check.

### WR-04: The rain/wind legend overflows the card at the default/minimum width and is clipped

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraph.qml:97-227`, `WeatherGraphMath.js:1106-1115`

**Issue:** The rainwind legend has five entries. Each is 6 (dot) + 4 + 14 (swatch) + 4 + label at 12px, with 10px spacing, which totals about 308px. At the 900px minimum the cards' inner width is about 278px. `legendRow` is a plain `Row` with no elide, wrap or scale. `WeatherBaseCard` has `clip: true`, so the last entry ("Vis") is cut off.

**Fix:** Use a `Flow` (wrapping), or shrink the label size and spacing when `legendRow.implicitWidth > legendRow.width`. At minimum, add a harness check that compares the legend's implicit width against `(MIN_OUTER_W - chrome - 24) / 3 - 20`.

### WR-05: Removing the scroll container lets content become unreachable when the alert drawer or banner is tall

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherPopup.qml:56-62`, `WeatherGraphMath.js:126-129`

**Issue:** `height = Math.min(maxH, Math.max(minContentH, ...))`. If `alertBanner` grows past the cap (its advisory drawer expands with `WordWrap` text, `WeatherAlertBanner.qml:143-160`), `minContentH` can exceed `maxH`:

`alertBanner.implicitHeight + heroCard.implicitHeight + 24 + 240 > maxH`

The height is then capped at `maxH`, but the `ColumnLayout` children still demand their minimum sizes (`graphArea` has `Layout.minimumHeight: 120`). The content overflows the bottom of `contentRoot` and the layer-shell window. The 54.3 `StyledFlickable` let the user scroll to it; nothing does now. The popup height also resizes on every frame of the Revealer animation.

**Fix:** Cap the drawer height inside `WeatherAlertBanner`, for example `Layout.maximumHeight` with its own small `Flickable` limited to the alert text. Alternatively, have `popupContentSize` report `overflow: minContentH > maxH` and shrink the graph row's minimum. Do not let the layout overflow without warning.

### WR-06: Popup size math ignores the vertical-bar geometry

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:125-126`, `WeatherPopup.qml:56-62`

**Issue:** `maxW = sw - 2*edgeGap - chrome` assumes the popup can use the full screen width. In vertical-bar mode, `StyledPopup` places it at `lockedLeftMargin = Appearance.sizes.verticalBarWidth`, so at `popupWidthPercent` near 100 it extends `verticalBarWidth - edgeGap` px past the right edge. `maxH` also always subtracts `barHeight`, which does not exist in vertical mode. `sanePercent` allows up to 100, so this is reachable from `config.json`.

**Fix:** Pass the bar orientation in `opts`:
```js
var barW = isNum(o.barWidth) ? o.barWidth : 0;   // verticalBarWidth when vertical, else 0
var maxW = sw - barW - 2 * edgeGap - chrome;
var maxH = sh - barHeight - 2 * edgeGap - chrome; // pass barHeight: 0 when vertical
```
and pass `barWidth`/`barHeight` from `Config.options.bar.vertical` in `WeatherPopup.qml`.

### WR-07: Assert harness fails open and its QML gate checks syntax only, so it cannot catch the load-time bug class seen before

**File:** `scripts/phase54.4-weather-assert.sh:215-218`, `:371`, `:468`, `:483-503`

**Issue:**
- If `node` is missing, every `WeatherGraphMath.js` vm assertion (sections 2-5) becomes a single `finding`. Findings do not count toward the exit code (`exit "$FAIL"`), so the harness passes with zero math coverage. Missing `qmlformat` is handled the same way.
- The only QML gate is `qmlformat -n`, which is a parser. It cannot detect default-property type mismatches, unknown properties, wrong property types or unresolved ids. That is the class of the earlier `Connections`-in-`StyledPopup` load failure (566f57ee).
- The guard added in its place (`grep -cE '^    [A-Z]...\{'`) depends on indentation. It misses a top-level object written with a different indent, or an inline `property Connections c: Connections {}`.

**Fix:** Make a missing `node` a `fail` (or require `--allow-missing-node`). Add a real type check such as `qmllint -I <quickshell qml import path> -I "$II_ROOT"` with the `qs` module mapped, failing on `[missing-property]`, `[incompatible-type]` and `[unresolved-type]`. Or add a short headless load (`QT_QPA_PLATFORM=offscreen qml -I ...`) of a stub that instantiates `WeatherPopup`.

### WR-08: Peak labels can be drawn over the EPA ribbon and over bars, contrary to D-54.4-27/29

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:1577-1582`

**Issue:** `drawKind` always calls `placeLabels(..., { bottom: geom.plotBottom }, [])`, so nothing is ever reserved.

For airuv, the series live above `airuvRibbonTop(geom) = plotBottom - 6`. A "below" pressure-low label at marker y in `(plotBottom-19, plotBottom-13]` passes the bounds test but covers the ribbon. No bar rects are reserved either, so rain/wind/vis/UV labels can sit on top of mm or solar bars. The `placeLabels` doc says reserved rects are honoured, but the only caller passes none.

**Fix:**
```js
var reserved = [];
if (kind === "airuv") reserved.push({ x: geom.plotLeft, y: airuvRibbonTop(geom), w: geom.plotRight - geom.plotLeft, h: RIBBON_H });
// optionally push mmBarRects / solarBarRects too (excluding each bar's own bar-top label)
drawLabels(ctx, placeLabels(cands, bounds, reserved));
```

### WR-09: Missing raw fields are turned into real-looking readings (0°C, 0 km "Fog", UV 0)

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:160-225` (`normalizeRawHour`), `:141-149`

**Issue:** In the `Weather.hourly` fallback path:
- A missing or unparsable `tempC`/`FeelsLikeC` becomes `0`.
- A missing `visibility` becomes `0`. It is then drawn as a red "Fog" segment, peaks and tooltips read "0 km Fog".
- UV, wind and humidity also default to `0` through `_int`/`_float`.

`seriesRuns` only breaks a run on non-finite values, so these zeros are plotted as real data. Pressure is the only field where 0 is treated as missing. This contradicts the module's own rule ("A missing value breaks the run").

**Fix:** Return `null` for unparsable values in the graph normaliser (`function _intOrNull(v) { var n = parseInt(v, 10); return isNaN(n) ? null : n; }`) and let `isNum` drop them. `Weather.qml rebuildTimeline()` has the same pattern (`parseInt(r.visibility, 10) || 0`), outside this diff.

### IN-02: Temperature y-labels can still overlap on wide ranges

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:1147-1152`

**Issue:** `labelStep` is only ever 1 or 2. When `rowPx < 6` (for example a 30°C range on a 150px plot), 10px labels drawn every 2° overlap.

**Fix:** `labelStep = Math.max(1, Math.ceil(12 / rowPx))`.

### IN-03: The pressure trend for the first slots compares over 1-2 hours, not ~3

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraphMath.js:593-619`

**Issue:** For `i = 1` or `2`, the nearest earlier reading to `i-3` is slot 0. The 1-2h delta is labelled Rising or Falling against the same 1 hPa threshold as the 3h trend.

**Fix:** Require `i - j >= 2` (or scale the threshold by `(i - j) / 3`); otherwise return no trend.

### IN-04: Two different definitions of "is the 25-slot timeline"

**File:** `WeatherGraph.qml:21` (`isNow !== undefined`) vs `WeatherGraphMath.js:1604-1606` (`isNow === true`)

**Issue:** The axis "Now" label and the backdrop hairline use the QML definition; the tooltip lead uses the GM one. They agree today only because `Weather.qml` always sets `isNow` true at index 12.

**Fix:** Bind `readonly property bool isTimeline25: GM.isTimeline25(root.validHours)`.

### IN-05: `updateLockedMargins` dereferences `root.hoverTarget` without a guard and now runs on more paths

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/StyledPopup.qml:90-92`, `:101-103`, `:124-129`

**Issue:** `root.hoverTarget.width` throws a TypeError if `hoverTarget` is null. The new `Connections` calls this on every implicit-size change, including during construction.

**Fix:** `if (!root.hoverTarget) return;` at the top of `updateLockedMargins()`.

### IN-06: The canvas is not repainted on theme change; units ignore `useUSCS`

**File:** `restow/quickshell/.config/quickshell/ii/modules/ii/bar/weather/WeatherGraph.qml:76-83`, `:352-373`

**Issue:**
- `theme()` is only read inside `onPaint`, and nothing triggers `requestPaint()` when `Appearance.colors.*` change. After a wallpaper or scheme switch with the popup open, the grid, text, shade and Now colours stay stale until the next data refresh or reopen.
- Tooltips hard-code `°`, `km/h` and `km`. `Config.options.bar.weather.useUSCS` has no effect here. This was already true before the phase.

**Fix:** Add `Connections { target: Appearance.colors; function onColOutlineVariantChanged() { root.requestRepaint(); } ... }`, or bind a `readonly property var _theme: root.theme()` with an `on_ThemeChanged` repaint.
