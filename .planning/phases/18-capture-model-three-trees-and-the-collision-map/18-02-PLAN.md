<objective>
Create the two missing trees and give all three a README that makes a file's capture mechanism
answerable from its location alone — which is the whole of CAP-01.

Each README carries D-12's four parts: a one-paragraph contract stating what the installer does to
files in that tree, the exact recovery command, the membership rule, and — for `restow/` only — a
generated package-to-tag-to-recovery table whose region the generator owns (that table is populated
in plan 18-10, once the packages exist).

`stow/README.md` is also where the CAP-07 ban lands. GNU Stow's own conflict message advertises the
banned flag, so the ban needs its documented exception and, beside it, the legitimate procedure that
makes reaching for the flag unnecessary (RESEARCH F-2).

Purpose: make location the answer, and make the two things an operator reaches for under pressure —
recovery after an install, and the flag stow suggests when it conflicts — documented in the place
they will actually look.
Output: `stow/README.md`, `restow/README.md`, `capture/README.md`, `docs/archive/README.md`, and
assert sections 1 and 5.
</objective>

    `stow/README.md`:
    - Contract: the installer never collides with anything in this tree. The live path stays a symlink
      and the repo copy is never written through. The map predicate for membership is: a package
      belongs here when every map row at or above its destinations has `symlink_outcome` preserved and
      `repo_outcome` untouched (D-05).
    - Recovery: nothing to recover after an install. State the re-link command anyway, for a fresh
      machine or after a manual unlink: the fixed idiom from `arch/kitty.sh:10`, which is
      `cd` into the tree then `stow` with the verbose and no-folding flags in that order, target `~`,
      package name last. `--no-folding` applies uniformly across all three trees (D-14): one idiom in
      every call site, one thing for the assert to check, and a smaller blast radius when a partial
      failure leaves a tree half-written.
    - Membership: prefix matching, per D-13 — a package belongs in `restow/` if any file it installs
      sits at or under a `dest` row whose outcome is destroyed or repo-overwritten, because
      `rsync --delete` does not care that the link is one level down inside the directory it replaces.
      Exact-path matching was rejected: it would make membership depend on which files happen to exist
      on the host, destroying the host-independence the map's literal XDG paths establish.
    - A section titled for the upstream quirk RESEARCH F-4 measured: `install_dir__ignore_existing`
      short-circuits on the whole destination directory, not per file. Once `~/.config/hypr/custom`
      exists, a *new* file added upstream under `dots/.config/hypr/custom/` is never installed. The
      primitive's name promises per-file merge semantics; the wrapper function delivers all-or-nothing
      directory semantics. That is a benefit for membership here and a trap for anyone expecting
      upstream additions to appear.
    - A section titled "The banned stow flag and the procedure that replaces it", covering CAP-07:
      state the ban — the flag appears in no script under `arch/` or `scripts/` — and why: RESEARCH F-7
      reproduced it exiting 0 while silently replacing repo content with live content, which is a
      successful-looking run that destroys the authoring copy. State the exception exactly as the
      ROADMAP fixes it: interactive use only, on a clean tree, one path at a time.
    - Immediately beside it, the procedure that makes the flag unnecessary, because GNU Stow's own
      conflict message names the flag when it refuses (RESEARCH F-2): when the live path is a real
      file rather than a link, run the simulate form first with the `-n` flag to get the exact conflict
      list, decide which copy wins, move the live file aside rather than deleting it, run the real
      stow, confirm with `test -L`, and only then remove the aside copy in a later commit.

    `restow/README.md`:
    - Contract: the installer overwrites into this tree. Either the live symlink is destroyed and
      replaced with a real file, or the installer writes straight through the link and corrupts the
      repo copy. Which of the two is recorded per package as its tag.
    - The two tags and their recovery, derived from the map's two *outcome* columns and not from the
      `primitive` column (D-09): `rsync-replace` means the symlink was destroyed and the repo copy is
      untouched — recover by re-stowing. `cp-through` means the symlink survived and the repo copy was
      overwritten — recover with `git checkout` on the repo path, then re-stow. Deriving from the
      outcomes rather than the primitive means the tag comes from the same source as the `tree` column
      and a new primitive needs no second lookup table.
    - The vocabulary caveat D-09 requires: `rsync-replace` is the wording `.planning/ROADMAP.md` fixes
      for CAP-01, so it is kept verbatim even though two of its members —
      `install_file__auto_backup` and the inline rename at `3.files-legacy.sh:51-54` — destroy the link
      with `mv` rather than with rsync. The tag names the recovery, not the tool.
    - Recovery text appears exactly once, in the generated table (D-12). The prose and D-10's
      documented recovery both point at that table rather than restating the commands, so a tag
      correction cannot leave a stale copy behind. D-10 also records what does *not* ship: no

      accepted cost is that the operator runs the recovery command after a dots-hyprland install.

      duplicated across `stow/` and `restow/` — `hypr/custom/` is preserved by the installer and
      `hypr/hyprland/` is destroyed by it, so the tree decides the meaning of the name. Meanwhile
      `restow/starship/` is named for the single file it carries. Nothing breaks today, because
      `verify` takes no arguments (D-53) and no script takes a bare package name, but a future command
      that did would find `hypr` ambiguous.

      slot for answering it later.
    - The Q-2 call-site boundary: `arch/zsh_powerlevel.sh` independently stows the `zsh` package but
      does **not** get a starship line. It is a prompt-theme installer and does not own starship.
