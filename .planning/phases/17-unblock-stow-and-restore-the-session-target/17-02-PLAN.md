<objective>
Make `arch/dots-hyprland.sh` incapable of deleting anything inside the repo, and make the
file safely sourceable so that guarantee can be tested as a library function rather than
inferred from reading.

Purpose: `safe_rm_path` is the chokepoint for all seven destructive call sites in the
uninstall path. Once v0.4 starts capturing live configuration into the repo, an uninstall
that reaches a repo path deletes captured configuration. The repo lives inside `$HOME` on
this machine, so every repo path already passes the existing allow-list — the new clause is
the only thing standing between the uninstaller and the capture trees.
Output: one guarded function, one dispatch guard, four assert sections, one re-pinned
sibling baseline.
</objective>

phase-level decision.

**Signal 1 — `pluralization`.** The success criterion adds a third refusal case to
`safe_rm_path` "alongside the existing" two. The question: is an ad-hoc list of `case` clauses
still the right identity model for "a path this tool refuses to delete", now that there are
three protected regions rather than two?

- **Primary noun:** *protected region* — the thing `safe_rm_path` actually reasons about.
- **Decision:** `add-alongside`, with the generalisation deliberately not taken.
- **Rationale:** the locked decisions specify a third refusal clause in the same function, not a
  new abstraction, and the three regions have genuinely different comparison semantics — one is
  a glob allow-list, one is a glob refusal, and the new one is a resolved-path prefix compare.
  A data-driven protected-region list would have to carry a per-entry comparison kind, which is
  more machinery than three clauses.
- **Accepted debt, and what would force a promote:** a *fourth* protected region. Phase 18
  introduces two more capture trees and Phase 22 adds a guard list of generated paths. If any of
  those needs the uninstaller to refuse it, the case-clause form stops being the right shape and
  the promote to a declared region list should happen then, not incrementally.

**Signal 2 — `chosen`.** The startup trigger moved from a fixed compositor-configuration line to
a chosen overlay file (`custom/execs.lua`). **Decision:** `no-change`. This is not a
configuration decision becoming a modeling decision — the overlay slot is the vendor's own
sanctioned extension point, required conditionally by the compositor's Lua entry point, and the
repo is adopting it rather than inventing a selection mechanism.

**Companion invariant test (suggested, not required):** a check that the number of `return 1`
refusal branches in `safe_rm_path` equals the number of protected regions the phase documents,
